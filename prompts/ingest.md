# Wiki³ Interactive Ingest

현재 사용자가 `raw/`에 추가한 자료를 개인적인 목적과 연결하여 Wiki에 반영하세요.

인제스트는 한 번에 끝내지 않습니다. 반드시 다음 두 단계로 나눕니다.

1. **소스 이해와 사용자 인터뷰**
2. **사용자 답변을 반영한 Wiki 업데이트**

사용자의 답변을 받기 전에는 `wiki/`를 생성하거나 수정하지 마세요.

## 0. 시작 전 확인

1. `WIKI_RULES.md`를 읽습니다.
2. 현재 사용자의 `member-id`를 확인합니다.
3. `members/{member-id}/CONTEXT.md`, `WIKI_SCHEMA.md`, `wiki/index.md`를 읽습니다.
4. `WIKI_SCHEMA.md`가 없으면 인제스트를 계속하기 전에 `prompts/wiki-init.md`로 개인 구조를 완성하도록 안내합니다.
5. `members/{member-id}/raw/`에서 새로 추가된 파일을 찾습니다.

새 파일이 하나면 그 파일을 대상으로 진행합니다. 여러 개이거나 어떤 파일인지 확실하지 않으면 파일명과 수정 시각을 보여주고 사용자에게 대상을 확인받습니다.

## 1단계: 원본 읽기

- 대상 파일을 읽기 전용으로 취급합니다.
- `raw/`의 파일을 수정, 이동, 이름 변경 또는 덮어쓰기하지 않습니다.
- 개인 `raw/` 원본은 로컬 전용이며 Git에 스테이징하거나 커밋하지 않습니다.
- 가능하면 읽기 전에 대상 파일의 SHA-256 해시를 기록하고 완료 후 다시 계산하여 동일한지 확인합니다.
- 파일 내용뿐 아니라 확인 가능한 경우 제목, 원문 URL, 작성자·발행처, 발행일, 캡처일도 확인합니다.
- 웹 클리퍼 문서의 광고, 메뉴, 추천 글처럼 본문이 아닌 요소는 분석에서 구분합니다.
- 원문에 없는 내용을 사실처럼 보충하지 않습니다.

## 2단계: 소스 분석 제시

Wiki를 수정하기 전에 사용자에게 다음 형식으로 소스 분석을 보여줍니다.

```markdown
## 소스 정보

- 파일:
- 제목:
- 작성자/발행처:
- 발행일 또는 데이터 기준일:
- 원문 URL:

## 한 문단 요약

## 핵심 주장 (Key Claims)

- 주장
  - 근거 또는 맥락:
  - 소스 내 상태: 사실 / 저자의 주장 / 예측 / 의견 / 불명확

## 언급된 엔티티 (Entities)

### 사람

### 조직

### 도구·제품·데이터

## 다루는 개념 (Concepts)

## 주의할 점

- 불확실한 주장
- 출처가 제시되지 않은 주장
- 작성 시점 때문에 현재와 달라질 수 있는 내용
- 기존 Wiki와 충돌할 가능성
```

단순히 이름이 한 번 나온 모든 대상을 엔티티로 분류하지 마세요. 글의 주장이나 현재 사용자의 프로젝트 이해에 의미가 있는 대상만 선정합니다.

## 3단계: 사용자 의도 인터뷰

소스 분석을 보여준 뒤 아래 질문을 **한 번에 하나씩** 물어봅니다.

1. 이 글을 왜 캡처했나요? 특히 중요하거나 눈에 걸린 부분은 무엇인가요?
2. 이 글이 지금 하고 있는 일이나 기존 생각과 어떻게 연결되나요?
3. 이 내용을 바탕으로 무엇을 조사, 검증, 설계 또는 실행해 보고 싶나요?

답변이 모호하면 각 질문마다 필요한 경우 확인 질문을 하나 할 수 있습니다. 사용자가 한 답변에서 다음 질문까지 이미 충분히 답했다면 같은 내용을 반복해서 묻지 않습니다.

각 답변은 사용자의 의견입니다. 원문의 주장이나 객관적 사실로 바꾸어 기록하지 마세요.

## 4단계: 반영 계획 수립

세 질문에 대한 답변을 모두 받은 뒤 기존 Wiki에서 다음을 검색합니다.

- 같은 소스를 이미 처리한 문서
- 같은 원본 경로나 SHA-256을 가진 기존 소스 요약
- 관련 엔티티와 개념 문서
- 사용자가 언급한 현재 작업, 가설 또는 목표
- 새 소스와 충돌하거나 보강되는 기존 주장

그리고 사용자에게 다음을 간단히 알립니다.

- 새로 만들 소스 요약 페이지
- 갱신할 기존 엔티티·개념·프로젝트 문서
- 새로 만들 필요가 있는 엔티티·개념 문서
- 발견된 충돌이나 미검증 사항

중복 문서가 생기지 않도록 기존 문서 업데이트를 우선합니다. 단순히 언급되었다는 이유만으로 엔티티·개념 페이지를 새로 만들지 않습니다.

## 5단계: Wiki 반영

반영 계획을 기준으로 다음 작업을 수행합니다.

### 소스 요약 페이지

`templates/source-summary.md`를 사용하여 `members/{member-id}/wiki/sources/` 아래에 생성합니다.

소스 요약에는 반드시 다음을 분리해서 기록합니다.

- 소스가 말하는 내용
- 사용자가 캡처한 이유
- 현재 작업 및 기존 생각과의 연결
- 사용자가 해보고 싶은 것
- AI가 발견한 연결 후보와 미검증 사항

### 엔티티·개념 페이지

- 관련 기존 페이지가 있으면 새 소스와 사용자 관점을 출처 링크와 함께 추가합니다.
- 기존 주장과 충돌하면 한쪽을 덮어쓰지 않고 양쪽 주장, 시점, 출처를 기록합니다.
- 새 페이지는 향후 다시 참조할 가치가 있을 때만 만듭니다.
- 소스의 주장, 사용자의 해석, AI의 추론을 명시적으로 구분합니다.

### 인덱스와 로그

- `wiki/index.md`에 새 페이지와 중요한 변경 문서를 연결합니다.
- `wiki/log.md`에 날짜, 인제스트한 원본, 생성·수정한 문서, 변경 이유를 기록합니다.
- 모든 Wiki 문서에서 원본의 상대 경로를 추적할 수 있게 합니다.
- 소스 요약에 원본 SHA-256을 기록하여 중복 인제스트와 원본 변경을 확인할 수 있게 합니다.
- 원본이 다른 clone에 없을 수 있으므로 URL, 작성자·발행처, 발행일·기준일, 캡처일을 가능한 범위에서 함께 기록합니다.
- `source_availability: local-only`를 기록하여 원본이 작성자의 컴퓨터에만 있다는 사실을 다른 참여자가 알 수 있게 합니다.

## 6단계: 완료 보고

사용자에게 다음을 알려주세요.

- 읽은 원본 파일
- 생성한 문서
- 수정한 문서
- 사용자의 답변이 어디에 반영되었는지
- 발견한 충돌, 불확실성 또는 추가 검증 과제
- `raw/`가 변경되지 않았다는 확인

## 7단계: Git 반영

사용자가 인제스트 완료 후 푸시까지 요청한 경우에만 다음을 수행합니다.

1. `git status`로 변경 범위를 확인합니다.
2. `members/{member-id}/raw/`가 스테이징되지 않았는지 확인합니다.
3. 현재 사용자의 `wiki/` 변경만 경로를 명시하여 스테이징합니다.
4. 인제스트 한 건을 설명하는 작은 커밋을 만듭니다.
5. `git pull --rebase origin main`으로 최신 변경을 반영합니다.
6. 충돌이 없을 때 `git push origin main`을 실행합니다.

`git add .`은 사용하지 않습니다. 다른 참여자의 개인 공간이나 공용 파일에 예상하지 못한 변경이 있으면 커밋하거나 충돌을 임의 해결하지 말고 사용자에게 알립니다.

## 사용자가 바로 쓸 수 있는 요청문

```text
나는 {member-id}야.
방금 웹 클리퍼로 내 raw/에 저장한 글이 있어.
prompts/ingest.md에 따라 대화형으로 인제스트해줘.
raw/는 절대 수정하지 마.
완료 후 내 wiki 변경만 커밋하고 main에 푸시해줘.
```
